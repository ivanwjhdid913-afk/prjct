# Четыре участка у устья Кузьминки

Сеть `kuzminka-v1` задаёт два входа, слияние и два последовательных участка
Воронежа ниже устья. Её геометрия воспроизводит [выбранную цепочку](kuzminka-network-chain.md)
по исходным вершинам OSM. Расходы, нагрузки, скорость и продольная дисперсия
в учебном сценарии требуют явного задания. Полевые измерения для их
валидации пока отсутствуют.

| ID участка | Начальный узел сети → конечный | OSM way и индексы включительно | Длина WGS84, м |
|---|---|---|---:|
| `voronezh-upstream` | `main-inlet` → `confluence` | 35164443 v29, 350…354 | 322.127224196 |
| `kuzminka-upstream` | `tributary-inlet` → `confluence` | 131324032 v16, 333…338 | 422.672333700 |
| `voronezh-below` | `confluence` → `section` | 35164443 v29, 354…358 | 430.380169078 |
| `voronezh-lower` | `section` → `outlet` | 35164443 v29, 358…360 | 158.640891585 |

| Узел сети | OSM node | WGS84 [долгота, широта] |
|---|---|---|
| `main-inlet` | 10758837678 | [39.7347544, 52.7695038] |

Роли `headwater` в JSON обозначают входы расчётной области на срезах рек.
В узле `confluence` сходятся две входящие ветви и одна исходящая.
В узле `section` одна входящая и одна исходящая ветвь. Общие концы
совпадают по исходному OSM node ID и координатам. Направление принято
по порядку исходных осей и проверено по топологии и региональным
географическим описаниям. Данные направления и их ограничения записаны
в `direction_basis`. [Описание Добровского округа](https://lipkray.ru/dobroe/priroda),
[описание Липецкого округа](https://lipkray.ru/lipetskr/priroda),
[правило OSM для осей водотоков](https://wiki.openstreetmap.org/wiki/Key:waterway).

В `metadata.verified_extension` отдельно сохранён следующий исходный
отрезок от 412452058 до 412452057 длиной **183.061680969 м**. Его конец
совпадает с картографическим началом боковой протоки. От слияния до этой
точки **772.082741631 м**. Продолжение предназначено для проверки
чувствительности к нижней границе. При его применении граница
должна учитывать присутствие протоки и выбранный режим. Установленные
расстояния и отсутствие дополнительных осей на четырёх коротких
отрезках приведены в [паспорте кандидата](kuzminka-confluence-candidate.md).
Сезонные связи, смешение, подпор и пригодность граничного условия
нуждаются в обследовании.

Сборщик проверяет оба хеша до записи. Координаты сохранены без упрощения,
привязки и интерполяции. `distances_m` — накопленные расстояния WGS84
GeographicLib от нуля для каждой вершины. Метаданные расстояний округляются
до микрометра для побайтовой воспроизводимости на Windows и Linux;
координаты исходных вершин и геодезические вычисления решателя не меняются.
Контрольная сумма
`metadata.geometry_sha256` равна
`34db5638470700df8e24bb8c13eaecb4d8309196e03f813c10360222e9816714`.
Она вычисляется как SHA-256 от UTF-8 JSON словаря `{"nodes": nodes,
"reaches": reaches}` с `sort_keys=True`, `separators=(',', ':')`,
`ensure_ascii=False`, `allow_nan=False`. Поля происхождения в
четырёх участках входят в эту сумму. Метаданные, включая отдельное
продолжение, защищены закреплёнными входными хешами и воспроизводимой
сборкой.

Из корня проекта после установки зависимостей backend выполняются

```powershell
backend/.venv/Scripts/python.exe backend/scripts/prepare_network.py
backend/.venv/Scripts/python.exe backend/tests/test_network_geometry.py
```

Выходной файл — `backend/data/networks/kuzminka-v1.json`. Проверки
сверяют длины, исходные вершины, общие узлы, накопленные расстояния,
контрольную сумму и повторное получение тех же байтов. Изменение
исходного снимка отклоняется до записи файла.
