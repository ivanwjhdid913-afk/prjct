# Наблюдения за водой

Локальная учебная основа веб-ГИС: каталог водных объектов с поиском и фильтрами, связанные точки наблюдения в списке и на карте Leaflet, карточка выбранной точки. Данные поступают из PostgreSQL/PostGIS через FastAPI в React.

Демонстрационный набор содержит **только синтетические записи**: учебную реку, озеро, водохранилище и четыре точки. Координаты вымышлены, положение точек на реальных водных объектах не подтверждено. Они не являются реальными станциями Липецкой области. Происхождение отмечено в базе (`is_synthetic`, `coordinate_source`), API и интерфейсе. Измерений, проб и импорта пока нет.

## Требования

- Docker Desktop с работающим движком Linux-контейнеров и Docker Compose.
- Git для истории исходников.
- Для дополнительных локальных проверок: Node.js 24 LTS с npm и Python 3.14. Для запуска через Compose отдельная установка PostgreSQL и Python-пакетов не требуется.

Начальная проверенная среда: Git 2.53.0, Node.js 24.21.0, npm 11.19.0, Python 3.14.1, Docker 29.8.2, Compose 5.6.0. Точные зависимости находятся в `frontend/package-lock.json` и `backend/requirements.txt`; прямые Python-зависимости — в `backend/requirements.in`.

## Первый запуск в Windows

Откройте PowerShell в папке проекта. Создайте локальный файл настроек, только если его ещё нет:

```powershell
if (-not (Test-Path .env)) { Copy-Item .env.example .env }
```

Перед первым запуском задайте собственный пароль в поле `POSTGRES_PASSWORD` файла `.env`. Этот файл исключён из Git. При уже созданном томе базы изменение только `.env` не меняет пароль пользователя PostgreSQL.

```powershell
docker compose up -d --build --wait
docker compose exec backend python -m app.seed
```

Первый запуск скачивает образы и зависимости. Миграции применяются при старте backend. Заполнение учебными объектами и точками выполняется отдельно и повторно не создаёт дубликаты; существующие записи и координаты не перезаписываются. К изменённым родительским демонстрационным объектам точки автоматически не присоединяются. Без заполнения показывается корректный пустой список.

- Интерфейс: <http://localhost:5173>
- API: <http://localhost:8000/api/v1/water-bodies>
- Описание API: <http://localhost:8000/docs>

Проверьте, что на экране три учебных объекта, их типы и маркировка «Синтетические данные». Нажмите «Обновить список». Данные приходят из базы, а не из встроенного массива интерфейса.

Введите часть названия, например `УЧЕБ`, выберите «Озёра» и нажмите «Применить» или Enter в поле поиска. Останется учебное озеро. Поиск не учитывает регистр, включая кириллицу и `ё`; пробелы по краям убираются. Пустой запрос не ограничивает название, «Все типы» не ограничивает тип. `%` и `_` ищутся как обычные символы. Поиск выполняется по подстроке, без морфологии и замены `ё` на `е`.

Изменение полей само по себе не отправляет запрос: действующие условия подписаны под формой. «Обновить список», повтор после ошибки и переходы между страницами сохраняют применённые условия. Применение или сброс возвращает на первую страницу. «Сбросить условия» очищает оба поля и сразу загружает полный список. Для проверки отсутствия совпадений совместите `РЕКА` с типом «Озёра»: интерфейс предложит изменить или сбросить условия. Пустая база имеет отдельное сообщение.

Повторный запуск: `docker compose up -d --wait`. После изменения исходников используйте `docker compose up -d --build --wait`. **Перед обновлением существующей базы с ревизии `0001` сделайте резервную копию по инструкции ниже:** запуск нового backend применяет миграцию `0002`, добавляющую точки. Затем отдельно выполните `docker compose exec backend python -m app.seed`, чтобы добавить демонстрационные точки. Применённая миграция `0001` не изменена.

У frontend есть HTTP healthcheck: ожидание готовности проверяет успешный ответ страницы и наличие входного модуля интерфейса. Остановка: `docker compose down`. Именованный том с данными сохраняется. **Не добавляйте `-v` к команде остановки: этот параметр удаляет том базы.**

## Точки наблюдения и карта

Нажмите название водного объекта в каталоге. У учебной реки три точки: две с координатами и одна без них. У озера одна точка, у водохранилища — пустой список. Нажмите точку в списке или её пронумерованный маркер: выбор синхронизируется, а карточка загружается отдельным запросом API. В ней показаны название, водный объект, долгота, широта и источник координат. Список и маркеры доступны с клавиатуры; маркер выбирается Enter или пробелом.

Точки без координат доступны в списке и карточке, но не имеют маркера; их количество указано отдельно. Если координат нет у всех точек, карта заменяется пояснением. При сбое подложки появляются сообщение и кнопка повтора, список и карточка продолжают работать. Цвет и обводка маркера обозначают только выбор, а не качество воды. Контуры водных объектов не строятся.

«Вернуться к каталогу» и кнопка «Назад» браузера сохраняют применённые поиск, тип и страницу в текущей вкладке. Состояние каталога хранится в памяти; перезагрузка страницы его сбрасывает. Экран объекта можно открыть ссылкой вида `http://localhost:5173/#water-body/<UUID>`.

Подложка — стандартные растровые тайлы [OpenStreetMap](https://www.openstreetmap.org/copyright) с видимой атрибуцией. Для локального интерактивного просмотра ключ и платный аккаунт не нужны. Используется HTTPS, стандартные Referer и кеш браузера; массового скачивания, предварительной загрузки и офлайн-карт нет. Доступность внешнего сервиса не гарантирована. Перед публичным развёртыванием или ростом нагрузки нужно заново проверить [политику тайлов OSM](https://operations.osmfoundation.org/policies/tiles/) и выбрать подходящий сервис. Запросы подложки передают серверу OSM обычные сетевые сведения браузера и область просмотра; имена точек не передаются.

Leaflet 1.9.4 поставляется с лицензией BSD-2-Clause; текст сохранён в `frontend/public/leaflet-license.txt` и доступен как `/leaflet-license.txt`. GeoAlchemy2 0.20.0 добавлен для связи SQLAlchemy с PostGIS; лицензия MIT сохраняется в установленном пакете. Версии зафиксированы в файлах зависимостей.

## Состав проекта

- `frontend/src/` — экран, состояния запросов и оформление; Vite передаёт `/api` в backend.
- `backend/app/` — подключение к базе, модель, API и отдельное заполнение учебными данными.
- `backend/migrations/` — начальная схема Alembic и включение PostGIS.
- `backend/tests/` и `backend/run_tests.py` — проверки на настоящем PostgreSQL в отдельной временной базе.
- `frontend/tests/` — браузерные сценарии Playwright.
- `compose.yaml` — база PostgreSQL 18/PostGIS 3.6, backend и интерфейс.

Сервисы доступны только через `127.0.0.1`: интерфейс — порт 5173, backend — 8000, база — 55432. Это локальное окружение разработки, без авторизации и публичного развёртывания. Для интерфейса используется сервер Vite; production-сборка также проверяется при создании образа.

SQLAlchemy отвечает за запросы и ограничения модели, Alembic — за версионирование схемы, Psycopg — за соединение с PostgreSQL. Положение хранится только в одном nullable-поле PostGIS `geometry(Point,4326)`: отдельных изменяемых столбцов широты и долготы нет. База проверяет тип, SRID, двумерность, непустую геометрию, долготу −180…180 и широту −90…90; NaN и бесконечности запрещены. Координаты не переставляются и не исправляются автоматически. Точка связана внешним ключом с водным объектом; источник координат обязателен даже для синтетической записи, а для точки без положения указывается причина его отсутствия. Служебные таблицы расширения исключены из сравнения Alembic.

## API

`GET /api/v1/water-bodies?limit=50&offset=0&q=учеб&kind=lake`

Ответ содержит `items`, `total` (число совпадений во всей базе), `catalog_total` (число объектов без фильтра), `limit`, `offset`. У каждого объекта есть UUID `id`, `name`, `kind` (`river`, `lake`, `reservoir`) и обязательный `is_synthetic`. Записи упорядочены по названию и ID. Допустимый `limit`: 1–100; `offset` — неотрицательное целое число.

Необязательный `q` — подстрока названия, максимум 120 символов исходного параметра до удаления пробелов; нулевой символ запрещён. Необязательный `kind` допускает только `river`, `lake`, `reservoir`. Для всех типов параметр `kind` нужно опустить; пустое значение недопустимо. Условия соединяются через AND и применяются до пагинации. Лимиты проверяются на backend; SQL-шаблоны из пользовательского ввода не исполняются.

Пустая база и отсутствие совпадений возвращают `200` и `items: []`; их различает `catalog_total`. Неверные параметры поиска, типа или пагинации — `422`. Недоступность базы — `503` с нейтральным сообщением без строки подключения. Имён, координат и характеристик реальных объектов в демонстрационном наборе нет.

`GET /api/v1/water-bodies/{water_body_id}/observation-points` возвращает `water_body`, полный массив `items` и `total`. В этом этапе коллекция точек не ограничена и не разбита на страницы: карта и список показывают весь набор выбранного объекта. Большие наборы потребуют отдельного решения по загрузке и отображению; интерфейс отвергает ответ, если `total` не совпадает с длиной массива.

`GET /api/v1/observation-points/{point_id}` возвращает отдельную точку и её `water_body`. Поля точки: `id`, `name`, `water_body_id`, `is_synthetic`, `coordinate_source`, `geometry`. Геометрия — GeoJSON `{"type":"Point","coordinates":[39.25,52.75]}`: **долгота, широта**, WGS 84 / EPSG:4326; отсутствие положения — `null`. Leaflet получает преобразованный порядок широта/долгота только при отображении.

Неизвестный UUID объекта или точки — `404`, некорректный UUID — `422`, отсутствие точек у известного объекта — `200` с пустым `items` и `total: 0`, недоступность базы — `503`. API создания и изменения точек в этот этап не входит.

## Проверки

На запущенном Compose:

```powershell
docker compose exec backend python run_tests.py -q
docker compose exec backend python -m pip check
docker compose exec backend alembic check
docker compose exec frontend npm run build
```

`run_tests.py` создаёт отдельную базу `water_test_<случайный UUID>`, применяет миграции и запускает pytest. Затем удаляет только созданную им базу. Рабочие таблицы не очищаются и не заполняются тестовыми наборами. Прямой `pytest` без изолированного окружения завершается до загрузки приложения; используйте команду выше. Пользователю локальной БД нужны права создания баз. После принудительного завершения процесса может остаться временная база: удалять её следует только после проверки имени и отсутствия работающего теста.

Браузерные тесты запускаются из Windows при работающем Compose:

```powershell
cd frontend
npm.cmd ci
$env:PLAYWRIGHT_BROWSERS_PATH = Join-Path (Split-Path (Get-Location) -Parent) '.cache\browsers'
npx.cmd playwright install chromium
npm.cmd test
```

Успешные сценарии каталога, точек и проверки размеров экрана используют настоящий API и базу с учебными записями. Пустые и ошибочные ответы, запоздалые ответы и пагинация дополнительно моделируются в браузере. Публичные тайлы в автотестах перехватываются: проверки не нагружают OSM и не зависят от доступности интернета. Реальный пустой список и недоступность соединения отдельно проверяются backend-тестами. Это не проверка реальных экологических данных.

При проверке картографического этапа прошли **60 backend-тестов** и **32 браузерных сценария Chromium**, сборка TypeScript/Vite, `pip check`, `alembic check` и ожидание готовности трёх контейнеров. Проверены привязка точки к объекту, координаты и их ограничения, отсутствие положения, ошибки API, повторяемый seed, миграция `0001 → 0002 → 0001 → 0002` на отдельной базе, выбор через карту/список/клавиатуру, сохранение условий и страницы каталога, отказ и восстановление подложки. Резервная копия перед миграцией восстановлена в отдельную базу с тремя объектами и ревизией `0001`. Настоящая подложка OSM дополнительно проверена во встроенном браузере.

Существующие проверки кириллицы, буквальных `%` и `_`, всех типов, сочетания условий, валидации, сброса, пагинации и запоздалых ответов сохранены. Backend-пагинация проверена на временных записях изолированной базы; браузерная пагинация и запоздалые ответы моделируются. Поиск, каждый тип и выбор точек проверены также через настоящий API с учебным набором.

Проверены экраны шириной 375, 768, 1024 и 1440 пикселей и управление с клавиатуры. На первом этапе также проверены сохранность записей после остановки Compose, откат и повторное применение миграции в отдельной временной базе и восстановление резервной копии с тремя записями и ревизией `0001`. Firefox, Safari, публичное развёртывание и нагрузочное тестирование не проверялись.

Если страница недоступна, проверьте `docker compose ps` и `docker compose logs --tail 50 backend frontend`. При ошибке соединения с Docker запустите Docker Desktop. При занятых портах остановите другой экземпляр этого проекта.

## Сохранение и восстановление

Исходники сохраняются локальными коммитами в рабочей ветке. Коммит не включает базу, `.env`, скачанные зависимости и результаты тестов. Для возврата к предыдущей версии кода предпочтительна отмена нужного коммита через `git revert` после проверки несохранённой работы и совместимости схемы.

Остановка и повторный запуск Compose сохраняют данные в томе `water-observation_water-data`. Резервную копию базы можно получить так (каталог исключён из Git):

```powershell
New-Item -ItemType Directory -Force backups | Out-Null
$backupName = 'water-' + (Get-Date -Format 'yyyyMMdd-HHmmss') + '.dump'
docker compose exec -T db pg_dump -U water -d water -Fc -f /tmp/water-backup.dump
if ($LASTEXITCODE -eq 0) { docker compose cp db:/tmp/water-backup.dump "backups/$backupName" }
```

Сохраняйте `.env` отдельно в защищённом месте. Перед восстановлением определите требуемые версию кода, ревизию миграций и копию базы. Сначала восстановите архив через `pg_restore` в отдельную пустую базу и проверьте результат; не перезаписывайте рабочую базу без отдельного решения. Откат `0002` удаляет точки, сохраняя водные объекты; откат `0001` удаляет и таблицу объектов. Откат миграций не является повседневным способом восстановления.
