# Наблюдения за водой

Локальная учебная основа веб-ГИС: каталог водных объектов с поиском и фильтрами, связанные точки наблюдения на карте и сценарный расчёт переноса растворённых хлоридов. Данные каталога поступают из PostgreSQL/PostGIS через FastAPI в React; расчёт выполняется отдельным модулем Python без обращения к базе.

Тема проекта: «Разработка геоинформационной системы моделирования распространения загрязняющих веществ в поверхностных водах Липецкой области».

Демонстрационный набор содержит **только синтетические записи**: учебную реку, озеро, водохранилище и четыре точки. Координаты вымышлены, положение точек на реальных водных объектах не подтверждено. Они не являются реальными станциями Липецкой области. Происхождение отмечено в базе (`is_synthetic`, `coordinate_source`), API и интерфейсе. Измерений, проб и импорта пока нет.

## Требования

- Docker Desktop с работающим движком Linux-контейнеров и Docker Compose.
- Git для истории исходников.
- Для дополнительных локальных проверок: Node.js 24 LTS с npm и Python 3.14. Для запуска через Compose отдельная установка PostgreSQL и Python-пакетов не требуется.

Начальная проверенная среда: Git 2.53.0, Node.js 24.21.0, npm 11.19.0, Python 3.14.1, Docker 29.8.2, Compose 5.6.0. Точные зависимости находятся в `frontend/package-lock.json` и `backend/requirements.txt`; прямые Python-зависимости — в `backend/requirements.in`.

## Первый запуск в Windows

Откройте PowerShell в папке проекта. Создайте локальный файл настроек, только если его ещё нет:

```powershell
if (-not (Test-Path .env)) { Copy-Item .env.example .env }
```

Перед первым запуском задайте собственный пароль в поле `POSTGRES_PASSWORD` файла `.env`. Этот файл исключён из Git. При уже созданном томе базы изменение только `.env` не меняет пароль пользователя PostgreSQL.

```powershell
docker compose up -d --build --wait
docker compose exec backend python -m app.seed
```

Первый запуск скачивает образы и зависимости. Миграции применяются при старте backend. Заполнение учебными объектами и точками выполняется отдельно и повторно не создаёт дубликаты; существующие записи и координаты не перезаписываются. К изменённым родительским демонстрационным объектам точки автоматически не присоединяются. Без заполнения показывается корректный пустой список.

- Интерфейс: <http://localhost:5173>
- API: <http://localhost:8000/api/v1/water-bodies>
- Описание API: <http://localhost:8000/docs>

Проверьте, что на экране три учебных объекта, их типы и маркировка «Синтетические данные». Нажмите «Обновить список». Данные приходят из базы, а не из встроенного массива интерфейса.

Введите часть названия, например `УЧЕБ`, выберите «Озёра» и нажмите «Применить» или Enter в поле поиска. Останется учебное озеро. Поиск не учитывает регистр, включая кириллицу и `ё`; пробелы по краям убираются. Пустой запрос не ограничивает название, «Все типы» не ограничивает тип. `%` и `_` ищутся как обычные символы. Поиск выполняется по подстроке, без морфологии и замены `ё` на `е`.

Изменение полей само по себе не отправляет запрос: действующие условия подписаны под формой. «Обновить список», повтор после ошибки и переходы между страницами сохраняют применённые условия. Применение или сброс возвращает на первую страницу. «Сбросить условия» очищает оба поля и сразу загружает полный список. Для проверки отсутствия совпадений совместите `РЕКА` с типом «Озёра»: интерфейс предложит изменить или сбросить условия. Пустая база имеет отдельное сообщение.

Повторный запуск: `docker compose up -d --wait`. После изменения исходников используйте `docker compose up -d --build --wait`. **Перед обновлением существующей базы сделайте резервную копию по инструкции ниже:** запуск backend применяет недостающие миграции до `0003`. Ревизия `0002` добавляет точки, `0003` — сохранённые условия; прежние записи сохраняются. Если обновляетесь с `0001`, затем отдельно выполните `docker compose exec backend python -m app.seed`, чтобы добавить демонстрационные точки. Применённые миграции `0001` и `0002` не изменены.

У frontend есть HTTP healthcheck: ожидание готовности проверяет успешный ответ страницы и наличие входного модуля интерфейса. Остановка: `docker compose down`. Именованный том с данными сохраняется. **Не добавляйте `-v` к команде остановки: этот параметр удаляет том базы.**

## Точки наблюдения и карта

Нажмите название водного объекта в каталоге. У учебной реки три точки: две с координатами и одна без них. У озера одна точка, у водохранилища — пустой список. Нажмите точку в списке или её пронумерованный маркер: выбор синхронизируется, а карточка загружается отдельным запросом API. В ней показаны название, водный объект, долгота, широта и источник координат. Список и маркеры доступны с клавиатуры; маркер выбирается Enter или пробелом.

Точки без координат доступны в списке и карточке, но не имеют маркера; их количество указано отдельно. Если координат нет у всех точек, карта заменяется пояснением. При сбое подложки появляются сообщение и кнопка повтора, список и карточка продолжают работать. Цвет и обводка маркера обозначают только выбор, а не качество воды. Контуры водных объектов не строятся.

«Вернуться к каталогу» и кнопка «Назад» браузера сохраняют применённые поиск, тип и страницу в текущей вкладке. Состояние каталога хранится в памяти; перезагрузка страницы его сбрасывает. Экран объекта можно открыть ссылкой вида `http://localhost:5173/#water-body/<UUID>`.

Подложка — стандартные растровые тайлы [OpenStreetMap](https://www.openstreetmap.org/copyright) с видимой атрибуцией. Для локального интерактивного просмотра ключ и платный аккаунт не нужны. Используется HTTPS, стандартные Referer и кеш браузера; массового скачивания, предварительной загрузки и офлайн-карт нет. Доступность внешнего сервиса не гарантирована. Перед публичным развёртыванием или ростом нагрузки нужно заново проверить [политику тайлов OSM](https://operations.osmfoundation.org/policies/tiles/) и выбрать подходящий сервис. Запросы подложки передают серверу OSM обычные сетевые сведения браузера и область просмотра; имена точек не передаются.

Leaflet 1.9.4 поставляется с лицензией BSD-2-Clause; текст сохранён в `frontend/public/leaflet-license.txt` и доступен как `/leaflet-license.txt`. GeoAlchemy2 0.20.0 добавлен для связи SQLAlchemy с PostGIS; лицензия MIT сохраняется в установленном пакете. Версии зафиксированы в файлах зависимостей.

## Состав проекта

- `frontend/src/` — экран, состояния запросов и оформление; Vite передаёт `/api` в backend.
- `backend/app/` — подключение к базе, модель, API и отдельное заполнение учебными данными.
- `backend/migrations/` — начальная схема Alembic и включение PostGIS.
- `backend/tests/` и `backend/run_tests.py` — проверки на настоящем PostgreSQL в отдельной временной базе.
- `frontend/tests/` — браузерные сценарии Playwright.
- `compose.yaml` — база PostgreSQL 18/PostGIS 3.6, backend и интерфейс.

Через `127.0.0.1` доступны интерфейс (5173) и backend (8000). PostgreSQL по умолчанию доступен только внутри Compose как `db:5432`: приложению и тестам внешний порт базы не нужен. Штатный запуск не требует локальных файлов из `.cache`. Это локальное окружение разработки, без авторизации и публичного развёртывания. Для интерфейса используется сервер Vite; production-сборка также проверяется при создании образа.

Если нужен внешний клиент PostgreSQL, явно подключите дополнительную конфигурацию:

```powershell
docker compose -f compose.yaml -f compose.db-access.yaml up -d --wait
```

Она открывает только `127.0.0.1:55432`. Если этот порт занят или зарезервирован Windows, выберите свободный, например `$env:POSTGRES_HOST_PORT='54321'`, и повторите ту же команду. Менять системные настройки портов не требуется. Вернуться к штатному запуску можно командой `docker compose up -d --wait`; именованный том и внутренний адрес базы сохраняются.

SQLAlchemy отвечает за запросы и ограничения модели, Alembic — за версионирование схемы, Psycopg — за соединение с PostgreSQL. Положение хранится только в одном nullable-поле PostGIS `geometry(Point,4326)`: отдельных изменяемых столбцов широты и долготы нет. База проверяет тип, SRID, двумерность, непустую геометрию, долготу −180…180 и широту −90…90; NaN и бесконечности запрещены. Координаты не переставляются и не исправляются автоматически. Точка связана внешним ключом с водным объектом; источник координат обязателен даже для синтетической записи, а для точки без положения указывается причина его отсутствия. Служебные таблицы расширения исключены из сравнения Alembic.

## API

`GET /api/v1/water-bodies?limit=50&offset=0&q=учеб&kind=lake`

Ответ содержит `items`, `total` (число совпадений во всей базе), `catalog_total` (число объектов без фильтра), `limit`, `offset`. У каждого объекта есть UUID `id`, `name`, `kind` (`river`, `lake`, `reservoir`) и обязательный `is_synthetic`. Записи упорядочены по названию и ID. Допустимый `limit`: 1–100; `offset` — неотрицательное целое число.

Необязательный `q` — подстрока названия, максимум 120 символов исходного параметра до удаления пробелов; нулевой символ запрещён. Необязательный `kind` допускает только `river`, `lake`, `reservoir`. Для всех типов параметр `kind` нужно опустить; пустое значение недопустимо. Условия соединяются через AND и применяются до пагинации. Лимиты проверяются на backend; SQL-шаблоны из пользовательского ввода не исполняются.

Пустая база и отсутствие совпадений возвращают `200` и `items: []`; их различает `catalog_total`. Неверные параметры поиска, типа или пагинации — `422`. Недоступность базы — `503` с нейтральным сообщением без строки подключения. Имён, координат и характеристик реальных объектов в демонстрационном наборе нет.

`GET /api/v1/water-bodies/{water_body_id}/observation-points` возвращает `water_body`, полный массив `items` и `total`. В этом этапе коллекция точек не ограничена и не разбита на страницы: карта и список показывают весь набор выбранного объекта. Большие наборы потребуют отдельного решения по загрузке и отображению; интерфейс отвергает ответ, если `total` не совпадает с длиной массива.

`GET /api/v1/observation-points/{point_id}` возвращает отдельную точку и её `water_body`. Поля точки: `id`, `name`, `water_body_id`, `is_synthetic`, `coordinate_source`, `geometry`. Геометрия — GeoJSON `{"type":"Point","coordinates":[39.25,52.75]}`: **долгота, широта**, WGS 84 / EPSG:4326; отсутствие положения — `null`. Leaflet получает преобразованный порядок широта/долгота только при отображении.

Неизвестный UUID объекта или точки — `404`, некорректный UUID — `422`, отсутствие точек у известного объекта — `200` с пустым `items` и `total: 0`, недоступность базы — `503`. API создания и изменения точек в этот этап не входит.

## Сценарное моделирование

После запуска Compose откройте `http://localhost:5173/#model` или раздел «Моделирование». Для быстрого показа нажмите «Запустить демонстрацию», затем «Воспроизвести» (Дон, 0–4 ч). Для контрольного синтетического примера ниже выберите «Синтетический участок» и задайте длительность 24 ч. Выбирайте время и сегмент на карте или в списке: карта, профиль и таблица показывают одни и те же значения API. Шкала концентраций фиксирована на весь расчёт. Все концентрации — средние по отображаемым сегментам, расстояния подписаны для их центров.

Изменение формы не пересчитывает результат автоматически. До нового запуска прежний результат маркируется как относящийся к предыдущим условиям; его входные параметры доступны под профилем. При ошибке можно повторить запрос. Новый запрос отменяет ожидание старого, запоздалый ответ не заменяет актуальный. «Отменить ожидание» отменяет ожидание в браузере; сервер может завершать уже начатый ограниченный расчёт. Запуски не сохраняются в БД и после ухода из раздела теряются.

В режиме «Синтетический участок» геометрия, источник и гидрологические параметры полностью **синтетические** и не относятся к предприятию. Демонстрационная линия идёт на север по меридиану WGS84 от произвольно выбранной точки 40° в.д., 52,3° с.ш. Это условная линия, не подтверждённое русло. Её координаты вычисляются backend через интеграл меридионального радиуса эллипсоида и обратное решение длины дуги; градусы и пиксели не используются как метры. Независимый контроль `PostGIS ST_Length(geography)` проверяет общую длину и сегменты с допуском 1 см. Отображаемые 100 сегментов покрывают ровно заданную длину; выходной буфер в карту не включён. Источник сброса и расчётный участок не создают записей точек наблюдения.

### Постановка и численный метод

Модель описывает полностью перемешанное сечение после зоны смешения, один консервативный растворённый компонент и постоянную гидравлику. Учитываются течение и продольная дисперсия. Нет притоков, водозаборов, распада, сорбции, донного обмена и подпора. Волна изменения расхода при открытии выпуска не рассчитывается. Модель не предназначена для озёр, водохранилищ, струи возле трубы или нормативной оценки.

Внутри ядра используются м, с, кг/м³; `1 мг/л = 0,001 кг/м³`. При `Q = Qr + q` и `A = Q/u` решается:

```text
∂(A c)/∂t + ∂J/∂x = 0
J = Q c − A D ∂c/∂x
c(x,0) = cb
J(0,t) = Q cb + q (ce−cb) I(t)
∂c/∂x(Lcalc,t) = 0
```

Вход — полный массовый поток, не фиксированная концентрация. В постоянном режиме `I(t)=1`; в режиме конечного периода `I(t)=1` до времени `τ`, затем `0`. Расход `Q=Qr+q` не меняется: после `τ` поступающая вода имеет фоновую концентрацию. Расчётный буфер равен как минимум `max(0,1 L, 20 D/u)` с округлением вверх до целой ячейки. Для устойчивого учёта малого превышения решатель переносит `c−cb`, а затем добавляет постоянный фон: вход избыточной массы равен `q(ce−cb)I(t)`. Отрицательное превышение при чистых стоках допустимо, отрицательная полная концентрация не обнуляется искусственно.

Применены конечные объёмы с экспоненциально согласованным потоком между ячейками (Scharfetter–Gummel) и схема Crank–Nicolson по времени. Для шага `dx`, `Pe=u dx/D` поток на единицу площади между соседями имеет вид:

```text
j = u/(1−exp(−Pe)) · c_left − u/(exp(Pe)−1) · c_right
```

Один и тот же поток входит в соседние ячейки с противоположным знаком, обеспечивая баланс массы. `Pe ≤ 0,5`; шаг времени ограничен так, чтобы правая часть Crank–Nicolson оставалась неотрицательной, а матрица неявного шага была M-матрицей. Трёхдиагональная система решается методом прогонки. Обнуления отрицательных значений и искусственного затухания нет. Зависимости для вычислений не добавлены: ядро использует стандартную библиотеку Python.

Сначала по участку проходит и размывается фронт. При постоянной нагрузке установившаяся концентрация `c∞=(Qr cb+q ce)/(Qr+q)` постоянна вдоль участка: такое плато физически ожидаемо. Конечный период создаёт проходящий импульс; после окончания нагрузки максимум может находиться ниже по течению, пока ближние сегменты уже возвращаются к фону. `L/u` — характерное время переноса, не точный момент первого появления. Результат API содержит адаптивно выбранные реальные временные состояния, включая начальное и конечное, и 100 средних по отображаемым сегментам. Внутренняя сетка мельче; усреднение сохраняет массу.

Для контрольного синтетического примера: `Qr=10`, `q=0,1` м³/с; `cb=10`, `ce=100` мг/л; `u=0,25` м/с; `D=5` м²/с; `L=10000` м; длительность 24 ч. Контрольные величины: `A=40,4 м²`, нагрузка выпуска `0,010 кг/с`, сверх фона `0,009 кг/с`, `c∞=10,891089… мг/л`, `L/u=11,111… ч`. Сетка этого примера: 1100 ячеек по 10 м, буфер 1000 м, 5520 временных шагов примерно по 15,652 с.

### API и ограничения размера

`POST /api/v1/simulations`, JSON:

```json
{
  "river_flow_m3_s": 10,
  "effluent_flow_m3_s": 0.1,
  "background_mg_l": 10,
  "effluent_mg_l": 100,
  "velocity_m_s": 0.25,
  "dispersion_m2_s": 5,
  "length_m": 10000,
  "duration_hours": 24
}
```

Допустимы только конечные JSON-числа; строки, логические значения, лишние и пропущенные поля отклоняются. Диапазоны: `Qr 0,1–1000`, `q 0–100 м³/с`; `cb/ce 0–10000 мг/л`; `u 0,02–2 м/с`; `D 0,1–100 м²/с`; длина `100–20000 м`; длительность `0,1–48 ч`. Дополнительно до расчёта проверяются пределы: 6000 ячеек, 15000 шагов и 20 млн операций «ячейка × шаг». Поэтому некоторые сочетания допустимых отдельных значений отвергаются: нужно сократить участок/время или изменить физические параметры сценария. Размер входного тела ограничен 4096 байт, включая потоковые запросы. В одном процессе backend выполняется не более одного расчёта; очереди задач нет.

Ответ: `inputs`, `derived`, `distances_m`, `times_hours`, `concentrations_mg_l[time][segment]`, `geometry` (GeoJSON, долгота/широта), `scale_mg_l`, `diagnostics`, `temporal_resolution`, `provenance=synthetic`. Число сегментов — 100, число временных состояний переменное: до 2048. Фактический сериализованный ответ ограничен 5 МиБ. Ошибки: `422` — параметры/стоимость задачи, `413` — размер тела, `503` с `Retry-After` — занятый вычислитель. API не зависит от записей в БД, но запуск Compose сохраняет прежнюю проверку доступности каталога.

### Численная проверка

Ядро проверяется отдельно от API, карты и PostgreSQL:

```powershell
docker compose exec backend python -m pytest solver_tests -q -s
```

Для запуска без Docker из `backend` при установленных зависимостях проекта: `python -m pytest solver_tests -q -s`. Полный backend-набор, включая ядро и интеграционные проверки, запускается через `docker compose exec backend python run_tests.py -q`; он использует отдельную временную базу, а не рабочие записи. Браузерные проверки: `npm.cmd test` из `frontend` при работающем Compose.

Независимый точный контроль выведен в `solver_tests/test_numerical_accuracy.py`: собственная мода уравнения с теми же потоковой входной и нулевой градиентной выходной границами, но с неравномерным начальным профилем. При `a=u/(2D)`:

```text
c = B + exp(a x) [cos(k x) + (a/k) sin(k x)] exp(−λt)
λ = D k² + u²/(4D)
2 a k cos(k L) + (a²−k²) sin(k L) = 0
```

Подстановка даёт вход `u B` на единицу площади и нулевую производную на выходе. Сравниваются точные средние по ячейкам, полученные аналитическим интегрированием, а не значения в центрах. Непроверенная формула из внешнего документа не используется как эталон.

Проверки включают единицы, отсутствие источника (`q=0`, `ce=cb`), чистые стоки, балансы полной и избыточной массы, установившийся предел, влияние параметров, сеточную сходимость и удвоение буфера. Допуски:

| Проверка | Допуск и смысл |
|---|---|
| Балансы массы | Относительная невязка менее `10⁻⁹`; это контроль дискретного сохранения, не точности полевых данных |
| Точная собственная мода | RMS менее `2·10⁻⁵ кг/м³` на 80 ячейках; при удвоении сетки ошибка должна уменьшаться более чем в 3,7 раза — проверка второго порядка |
| Уточнение времени | На фиксированной сетке ошибка должна уменьшаться более чем в 3,8 раза; сравнение с малым временным шагом отделяет временную ошибку от пространственной |
| Демонстрация, первые 6 ч | Максимальная разница всех срезов при `dx/2` менее `0,003 мг/л`, при `dt/2` менее `0,0002 мг/л`; примерно 0,34% и 0,023% от превышения над фоном |

Итоговая проверка этапа: **115 backend-тестов** (включая 24 независимых теста ядра) и **44 браузерных сценария Chromium**, сборка TypeScript/Vite, `pip check`, `alembic check` и готовность трёх контейнеров. Сохранность прежних записей подтверждена совпадением контрольных сумм. В браузере проверены настоящий API, соответствие карты/профиля/таблицы, отмена ожидания, ошибки, устаревшие ответы и размеры экрана 375–1440 px.

RMS точной собственной моды на 20/40/80 ячейках: `2,48864·10⁻⁴ / 6,24086·10⁻⁵ / 1,56142·10⁻⁵ кг/м³`. В разделе «Моделирование» выберите «Реальное речное русло», затем подготовленный участок:

| Участок | ID | Длина | Проверенное продолжение |
|---|---|---:|---:|
| Дон ниже Ольховца, Лебедянский район | `don-olkhovets` | 3126,043 м | 1370,250 м |
| Воронеж у Жёлтых Песков, северная окраина Липецка | `voronezh-zheltye-peski` | 321,825 м | 480,752 м |

Для Дона сохранён OSM way **30428409 v32**; прежний участок и демонстрации доступны. Источники, ODbL, границы и подготовка — в [паспорте Дона](docs/river-data.md). Новый Воронеж подготовлен из **OSM way 26274036 v57**, снимок получен 24.10.2026, WGS84 / EPSG:4326. Его направление подтверждается совместно региональным географическим описанием и топологией сети, а положение — независимой Esri World Imagery. Пилот намеренно короткий: границы исключают видимые связи со старицами; городской подпруженный участок не используется. Основная линия и продолжение проверены отдельно. Идентификаторы, версии, лицензия, основания направления, исключённые варианты и воспроизводимая офлайн-подготовка приведены в [паспорте Воронежа](docs/lipetsk-river-data.md). Обычный запуск использует сохранённую геометрию без запросов к геоданным.

Задайте «Положение сценарного источника, м» числом, клавиатурой или ползунком. Либо нажмите **«Указать источник на карте»**, затем рядом с выбранным руслом. Привязка выполняется только к нему, на эллипсоиде WGS84, с максимальным расстоянием **75 м**. Далёкая точка и последние 100 м участка отклоняются с объяснением; прежний источник сохраняется. Отмена доступна кнопкой и Escape. Обычные клики и выбор расчётного сегмента источник не перемещают. На телефоне режим выбора закрывает перекрывающие панели и переносит фокус на карту; числовой ввод остаётся альтернативой.

Маркер показывает условную границу **после полного смешения**, а не предприятие, фактический выпуск или струю возле трубы. Отсчёт идёт от верхней границы подготовленного участка. Расчётная длина определяется оставшейся геометрией ниже источника и недоступна для произвольного изменения. Нужно оставить не менее 100 м русла; для нового Воронежа допустимое положение — от 0 до примерно 221,825 м. Перемещение источника и смена участка изменяют условия следующего расчёта. Предварительный просмотр подписан отдельно; кнопка «Показать рассчитанный результат» возвращает сохранённую геометрию, маркер и подписи завершённого расчёта. Программа не запускает расчёт автоматически. Несовместимые участок или источник отключают А/Б с пояснением, сохраняя закреплённый А. Обе прежние демонстрации выбирают Дон по ID независимо от порядка каталога.

Нажмите «Рассчитать». Для просмотра фронта с исходными параметрами выберите примерно 1–3 ч. Кнопки воспроизведения/паузы, скорость 0,5×–4× и перемотка управляют одним временем карты, профиля и таблицы. При 1× вся длительность воспроизводится примерно за 24 секунды просмотра. Между сохранёнными реальными моментами применяется **линейная интерполяция рассчитанных концентраций**; она подписана в интерфейсе и не означает дополнительное решение уравнения. Воспроизведение начинается только по кнопке, останавливается при перемотке и в конце. Шкала неизменна на протяжении одного расчёта; движение цвета не заменяет численные значения.

Расстояния и границы сегментов вычисляет GeographicLib 2.1 на эллипсоиде WGS84. Внутри каждого из 100 отображаемых сегментов сохраняются исходные вершины русла; сегмент не заменяется хордой между его границами. Расстояния профиля отсчитываются от сценарного источника. Числовой предварительный маркер использует эллипсоидальную интерполяцию WGS84; при выборе кликом сохраняется точная координата ответа API.

Пользовательские расходы, концентрации, скорость и дисперсия остаются сценарными. Средний модельный расход из геоданных не подставляется. Расчётная гидравлика постоянна; реальная геометрия не подтверждает это допущение. Проверка концентраций по наблюдениям не выполнена. Не учитываются ветвления, другие сбросы, озёра, водохранилища, химические реакции и локальная зона смешения.

Проверенное продолжение ниже отображаемого конца зависит от участка: **1370,250 м для Дона** и **480,752 м для Воронежа**. Если требуемый ядром буфер выходит за это продолжение или задача превышает вычислительные ограничения, API возвращает понятную ошибку и **не изменяет параметры автоматически**. Например, остаток 100 м при `D=5 м²/с`, `u=0,25 м/с` и длительности 2 ч превышает лимит шагов; отдельно проверен допустимый сценарий 0,1 ч с теми же остальными параметрами.

`GET /api/v1/river-reaches` возвращает `items` с подготовленными линиями, накопленными расстояниями вершин, метаданными и SHA-256 геометрии. `GET /api/v1/river-reaches/{reach_id}/source-snap?longitude=...&latitude=...` возвращает `reach_id`, `source_distance_m`, `coordinate` (`[долгота, широта]`), `distance_to_river_m` и `max_distance_m=75`. Неизвестный участок, некорректные координаты, слишком далёкий клик и недопустимый остаток русла дают `422`.

В реальном запросе `POST /api/v1/simulations` передавайте семь физических параметров без `length_m`, а также выбранный `reach_id` и `source_distance_m`. Произвольный `length_m` с реальным руслом отклоняется. Ответ содержит вычисленную длину в `inputs`, идентификатор и положение источника, его координаты, `reach_metadata`, общую линию и `segment_geometries` с сохранёнными изгибами. Синтетический запрос из восьми параметров продолжает работать.

### Воспроизведение нового участка

Выберите **«Воронеж у Жёлтых Песков»**, включите выбор источника и нажмите примерно в верхней четверти линии. Оставьте исходные сценарные `Qr=10`, `q=0,1 м³/с`, `cb=10`, `ce=100 мг/л`, `u=0,25 м/с`, `D=5 м²/с`; задайте общую длительность **1 ч**, ограниченный период загрязнения **0,1 ч**. Это явно заданный сценарий, без фактического промышленного выпуска. Нажмите «Рассчитать» и «Воспроизвести». Рассмотрите время около 0,1–0,3 ч, C(x), C(t) и переход к максимуму выбранного сегмента. После прохождения импульса ближние сегменты возвращаются к фону. Скорость просмотра меняет только продолжительность воспроизведения.

Маленький участок может требовать мелкого внутреннего шага. Например, источник у последних допустимых 100 м и длительность 4 ч могут превысить вычислительный лимит; API объяснит отказ. Значения пользователя не заменяются автоматически. Проверенный буфер нового участка ограничен 480,752 м, поэтому комбинации потока, требующие большего продолжения, отклоняются.

Пригодность нового пилота ограничена сценарной демонстрацией в пределах русла при принятых постоянных параметрах. Паводковые связи стариц, подпор при разных уровнях и пространственная гидравлика не проверены. Дата спутниковой съёмки неизвестна. Проверка геометрии не подтверждает расходы, концентрации или точность прогноза; прежние ограничения численной точности коротких пиков сохраняются.

## Сравнение сценариев А и Б

1. Откройте моделирование и нажмите «Запустить демонстрацию».
2. Закрепите успешный результат кнопкой «Закрепить как А» и выберите «Создать вариант Б».
3. Уменьшите «Концентрация стоков ce» со 100 до 50 мг/л и нажмите «Рассчитать Б».
4. Выберите модельное время и сегмент. Переключайте «Показать А» / «Показать Б»: карта сохраняет положение, время и выбранный сегмент. Числа А, Б и разница Б − А относятся к одному моменту и месту. Панель профиля показывает две кривые на одинаковых осях.

Шкала концентраций общая для обоих завершённых результатов за весь расчёт. Она не меняется при воспроизведении или переключении А/Б; одинаковым концентрациям соответствует одинаковый цвет. После нового расчёта Б общий диапазон может измениться. Уменьшение концентрации стоков вдвое не означает уменьшения полной концентрации в реке вдвое: модель учитывает фон и соотношение расходов.

Закреплённый А не изменяется при редактировании и пересчёте Б. Заменить его можно только отдельным действием. Участок, положение источника, вещество и длительность должны совпадать. Расходы, концентрации, скорость и продольную дисперсию можно менять в прежних пределах. Изменение геометрии, источника или длительности отключает сравнение с объяснением; одиночный расчёт остаётся доступен, А сохраняется.

Форма содержит редактируемые условия, карта — завершённый расчёт. Устаревший результат Б явно помечается; ошибка или отмена запроса не удаляет сохранённые результаты. Статусы доступны и при открытых мобильных панелях. Фокус переносится в параметры при открытии и возвращается на кнопку при закрытии; покрытые элементы карты и профиля исключены из клавиатурной навигации, управление временем доступно.

Результаты хранятся только в памяти открытого раздела: после перезагрузки страницы или выхода из моделирования они сбрасываются. Записи сценариев в базе не создаются. Оба сценария используют прежний API и численное ядро; реальные сбросы предприятий и проверка по наблюдениям в этот режим не входят.

Проверки этапа сравнения: **74 frontend-теста** прошли (70 браузерных Chromium и 4 проверки математики сравнения), включая неизменность А, общую шкалу, синхронизацию времени и значений, несовместимость условий, отмену и запоздалые ответы. **34 проверки расчётного ядра и геометрии** прошли; полный backend-набор в этом этапе повторно не запускался. TypeScript и production-сборка Vite успешны. Вручную пройден пример со снижением ce со 100 до 50 мг/л; снимки и запись воспроизведения проверены на размерах 1366×768, 1280×720, 375×812 и 375×667. ## Ограниченный период загрязнения

В параметрах модели выберите «Ограниченный период загрязнения» и задайте «Период загрязнения, ч»: положительное число не больше общей длительности расчёта. До этого времени действует `ce`, затем концентрация поступающей воды становится `cb`. Расходы, скорость, дисперсия и геометрия остаются постоянными. Это отключение добавочной загрязняющей нагрузки, **не моделирование закрытия водовыпуска**; гидравлическая волна не рассчитывается. Распад и искусственное самоочищение не добавлены.

Для демонстрации нажмите «Демонстрация периода» в параметрах: Дон ниже Ольховца, источник в начале, `Qr=10`, `q=0,1 м³/с`, `cb=10`, `ce=100 мг/л`, `u=0,25 м/с`, `D=5 м²/с`, период **0,5 ч**, расчёт **6 ч**. Геометрия реальная, все нагрузки и гидрологические параметры синтетические. Запустите воспроизведение: метка на шкале и состояние источника показывают окончание нагрузки. К 1 ч концентрация ближнего сегмента около 10,0002 мг/л; в 2 ч максимум около 10,5634 мг/л находится на 1,58 км; в 6 ч максимум на участке около 10,000016 мг/л при фоне 10. Это расчёт, а не измерение.

В «Профиль и показатели» переключаются C(x) и C(t). Сегмент выбирается на видимой карте или в списке. Курсор графика, числа и карта используют одно модельное время. Доступна таблица C(t). Раздел «Почему меняется окраска?» объясняет плато, движение после прекращения нагрузки и условную толщину линии. Профиль расположен отдельно от карты: справа на ноутбуке, снизу на телефоне. Его содержимое прокручивается независимо; источник и выбранный сегмент остаются в открытой части карты, управление временем доступно. При открытии профиля и выборе сегмента карта показывает их вместе, а во время воспроизведения сохраняет положение. Цветовая шкала и кнопка закрытия доступны и после прокрутки профиля.

Сравнение А/Б допускает постоянную и конечную нагрузки, а также разные периоды нагрузки, при прежних требованиях к одинаковой геометрии, источнику, веществу и общей длительности. Настройки каждого завершённого результата независимы; общая шкала фиксирована для обоих полных расчётов. Изменённые условия формы не меняют состояние источника и метку окончания у уже показанного результата.

В API добавлены `load_mode: "continuous" | "finite"` и `load_duration_hours: number | null`. Старые запросы без них означают постоянный режим; ответ возвращает нормализованные настройки. Для `continuous` период должен быть `null`, для `finite` — конечное положительное число не больше `duration_hours`. Внутренний шаг, содержащий окончание нагрузки, делится точно по этому моменту; событие не округляется до кадра. Баланс использует `M_excess,in=q(ce−cb)τ` и `M_in=Q cb T+M_excess,in` в единицах ядра. В массу области и выходной поток входит вычислительный буфер за отображаемым участком.

Карта и графики линейно интерполируют адаптивно сохранённые состояния. Ошибка этого представления контролируется относительно отклонения от фона на каждом сегменте; подробности и ограничения приведены ниже. Это не непрерывное аналитическое решение. Скорость воспроизведения изменяет только скорость просмотра, не физическое время. Постоянный режим и конечный период, равный всей длительности, дают прежние численные результаты.

Проверки: **184 backend-теста**, включая **62 численные/геометрические проверки**, прошли в изолированной временной базе. Проверены прежний численный результат, точное отключение между кадрами и шагами, балансы полной/избыточной массы, `q=0`, `ce=cb`, неотрицательность, аналитический контроль конечного импульса и сходимость второго порядка по пространству/времени. Для демонстрации максимальные изменения при `dx/2`, `dt/2`, удвоенном выходном буфере: 0,001872; 0,0000668; менее `10⁻¹⁰ мг/л`. **79 frontend-тестов** и сборка TypeScript/Vite успешны. Визуально проверены 1366×768, 1280×720, 375×812 и 375×667; сохранена запись окончания нагрузки, последующего переноса и возврата ближнего сегмента к фону. ## Короткие пики и временное разрешение

Интегратор и выдача результата используют разные сетки. Физическая схема, обычный внутренний шаг и точное разделение шага в момент отключения нагрузки сохранены. После каждого реального шага, включая части разделённого шага, записываются 100 средних концентраций и физическое время. Затем выбирается общая неравномерная сетка по всем сегментам. Обязательно остаются максимум и минимум каждого сегмента, момент отключения и прежние 49 равномерных моментов. Если при округлении времени получились полностью одинаковые время и все 100 значений, в выдаче остаётся одна копия состояния; шаги интегрирования и масса сохраняются. Остальные состояния добавляются, пока линейная интерполяция между сохранёнными точками не удовлетворяет допуску на всей частой траектории. Дополнительные состояния не создаются интерполяцией старых 49 кадров.

Для сегмента `j` масштаб сигнала — `Aj=max_t|Cj(t)−cb|`. Допустимая абсолютная ошибка выдачи — `max(0,01 Aj, 10⁻⁹ мг/л)`. Контроль выполняется по всем реальным внутренним состояниям; между ними это граница относительно их кусочно-линейного представления, а не доказательство точности непрерывного решения уравнения. Максимум и минимум частой записи сохраняются без ошибки амплитуды и времени. Возможный экстремум между внутренними шагами этой проверкой не оценивается. Пространственная и временная погрешности самого интегратора остаются отдельными ограничениями модели.

Ресурсы ограничены: **2048 выдаваемых состояний**, **16 МиБ** плоского массива частой траектории (время + 100 значений float64), **5 МиБ** фактического JSON-ответа с геометрией и **50 млн** проверок значений при отборе. Это лимит массива траектории, а не всей памяти процесса; рабочие массивы схемы и сериализация ограничены дополнительно числом ячеек, шагов и размером выдачи. Прежние пределы 6000 ячеек, 15000 шагов и 20 млн операций «ячейка—шаг» сохраняются. При превышении API возвращает `422` с причиной и предложением изменить длительность/параметры; автоматически снижать точность или менять условия он не будет.

`times_hours` содержит реальные возрастающие времена от 0 до `inputs.duration_hours`; строк концентраций столько же. `temporal_resolution` сообщает число сохранённых и опорных состояний, допуски, достигнутую ошибку, максимальный внутренний шаг, наибольший интервал выдачи и ресурсные пределы. Интерфейс проверяет временной массив и показывает сведения о разрешении. Большие промежутки допустимы на почти неизменном хвосте; их длина не задаёт разрешение короткого пика.

Воспроизведение и перемотка используют физические часы. При постоянной скорости равные интервалы модельного времени занимают равное время просмотра независимо от плотности сетки. А/Б могут иметь разные временные сетки: каждый результат интерполируется на общем времени, шкала и положение карты сохраняются. В C(t) выберите сегмент и нажмите **«Перейти к максимуму»** или **«Перейти к минимуму»**. Воспроизведение остановится на сохранённом экстремуме, значение и время подписаны как расчётная оценка; карта, C(x), C(t) и числа относятся к этому моменту.

По всем 100 сегментам ошибка сохранённого максимума и его времени относительно частой записи равна нулю; наихудшая ошибка интерполяции — **0,947631% амплитуды отклонения от фона**. Контроль только обычных внутренних шагов даёт первый максимум **10,499256** на **4,870130 с**. Дополнительно сохранённое состояние в точные 5 с выше на 1,345% этой амплитуды, что укладывается в требуемые 2%; это реальный разделённый шаг, а не искусственное усиление сигнала. Максимальный внутренний шаг — 0,974026 с. Входная добавочная масса — 0,045 кг, невязка — около `2,14·10⁻¹⁵ кг`.

Для `ce=0` аналогично сохраняется провал: минимум первого сегмента **9,943781 мг/л** в 5 с; наихудшая ошибка интерполяции также 0,947631% относительно глубины провала. В обоих случаях и в постоянном режиме все 49 прежних общих состояний совпадают с предыдущей реализацией без изменения чисел.

Проверки этапа временного разрешения: **209 backend-тестов** в отдельной временной базе и **95 frontend-тестов** (91 браузерный сценарий Chromium и 4 проверки математики сравнения). После восстановления сеанса целевые 16 проверок повторно прошли. TypeScript и production-сборка Vite успешны. Проверены пятисекундный пик и понижение относительно фона по всем 100 сегментам, 48-часовой горизонт с короткой нагрузкой, получасовая демонстрация, постоянный режим, балансы, пределы памяти/срезов/фактического ответа, совпадение машинных времён, некорректные временные массивы, разные сетки А/Б, постоянная физическая скорость воспроизведения и клавиатурное управление. Рабочие записи базы не изменялись.

Визуальная проверка и запись выполнены в Chromium на 1366×768, 1280×720, 375×812 и 375×667. Демонстрация показывает переход к ближнему пику в 5 с, максимумы среднего и дальнего сегментов, дальнейшее движение и возврат к фону. Физический телефон, Firefox/Safari, нагрузочное тестирование и сопоставление с реальными наблюдениями не проверены. Гарантия выдачи относится к частой траектории этой численной модели; экстремумы между её внутренними шагами и погрешность гидрологических исходных данных ею не охватываются.

## Дробные времена и полнота сравнения

Конечный момент результата точно равен запрошенной длительности: например, `0.1`, а не `0.10000000000000002`. Строгая проверка конечности, порядка, границ и числа времён сохранена. Концентрации, шаги интегрирования, баланс и момент отключения нагрузки не меняются. При редком совпадении машинных представлений времени возле события обычный соседний момент может быть закодирован ближайшим допустимым float с изменением не более двух ULP времени события; само событие и границы остаются точными. Это локальное устранение коллизии представления, а не округление всего массива или дополнительный расчётный кадр.

Таблица C(t) при сравнении использует **отсортированное объединение сохранённых времён А и Б**. Каждый результат интерполируется независимо. Переключение А/Б не меняет строки, страницу таблицы, модельное время или положение карты. Экстремумы обеих сеток присутствуют. Время показано в секундах и с точным представлением в часах; максимум — 4094 строки при двух сетках по 2048 состояний с общими границами. Таблица открывается по запросу и отображает по 100 строк; доступны все страницы, включая клавиатурное управление на телефоне. При воспроизведении неподвижная таблица не пересчитывается на каждом кадре.

Для проверки воспроизведите пятисекундный пример выше: сначала постоянный А с `q=0`, затем конечный Б с `q=0,1` и нагрузкой 5 с. Откройте C(t) и таблицу при активном А. В строке **5 с** значение Б — **10,5060 мг/л**, соответствующее сохранённому максимуму **10,505969208918035 мг/л**. Прежняя таблица на сетке А показывала максимум Б около 10,000603 мг/л. Переключите А/Б и убедитесь, что строки не изменились. На Дону задайте длительность 0,1 ч: расчёт теперь принимается интерфейсом.

### Точность короткого пика

Погрешность сохранения траектории, погрешность численной схемы и неопределённость физических исходных данных — разные величины. **Допуск выдачи 1% не гарантирует 1% точности самого пика.** Для импульса 3,6 с на синтетическом участке 1000 м обычная и уточнённая сетки дали амплитуды 0,072405266 и 0,077060065 мг/л: различие 6,0405% от уточнённого результата.

Раздельные исследования dx при постоянном dt и dt при постоянном dx, амплитуды и времена ближнего/среднего/дальнего пиков, ограничения и команда воспроизведения приведены в [численном отчёте](docs/short-pulse-convergence.md). За исходные 0,1 ч середина и конец участка ещё не пройдены пиком, поэтому они дополнительно проверены на горизонте 1,5 ч. Последовательные различия сокращаются, но наиболее подробная сетка не объявляется точным решением. Короткие импульсы в обычном интерфейсе предназначены для качественной иллюстрации; количественную точность необходимо подтверждать отдельным уточнением для конкретной задачи. Параметры пользователя автоматически не меняются.

Проверки исправления: **237 backend-тестов** в отдельной временной базе и **109 frontend-тестов** (105 браузерных Chromium и 4 проверки математики сравнения), TypeScript/Vite и контейнерная сборка. Сквозные регрессии с настоящим API охватывают 0,1; 0,2; 0,4; 0,7; 6,1 ч, постоянную и конечную нагрузку, обе геометрии и А/Б; отдельно проверено событие на одной трети 0,7 ч. Сохранены проверки некорректных временных массивов, баланса, прежних режимов, каталога и мобильной клавиатурной навигации. Контроль сходимости запускается отдельно и содержит автоматические проверки без подбора допуска амплитуды ради прохождения.

Визуально проверены 1280×720 и эмуляция телефона 375×667: дробный расчёт Дона, пятисекундный пик, переход к максимуму, разные сетки А/Б, полная таблица и последующее движение. Не проверены физический телефон, Firefox/Safari, полевые наблюдения и универсальная численная точность для всех допустимых параметров.

## Библиотека условий сценариев

В параметрах модели откройте **«Сохранённые условия»**, задайте название и нажмите **«Сохранить как новый сценарий»**. Enter в поле названия также сохраняет условия и не запускает расчёт. Сохраняется текущая валидная форма, даже если карта показывает прежний расчёт. Каждое сохранение создаёт отдельную запись: изменение формы и повторное сохранение не перезаписывают оригинал. Название — 1–120 символов после удаления крайних пробелов, без управляющих символов.

Библиотека показывает название, участок, режим нагрузки и дату по 20 записей на страницу. Кнопка **«Открыть»** восстанавливает геометрию, положение источника и параметры. Расчёт запускается только отдельным нажатием **«Рассчитать»**. Прежний результат сохраняет свои условия и подписи; при отличающейся форме появляется сообщение о необходимости пересчёта. Для сравнения закрепите результат как А, откройте совместимые условия и явно рассчитайте Б. Одинаковые участок, источник и общая длительность по-прежнему обязательны.

В PostgreSQL сохраняются **условия для повторного расчёта**, а не массивы концентраций, время воспроизведения или завершённая пара А/Б. Условия остаются после перезагрузки страницы и перезапуска приложения; результаты А/Б доступны только в текущем сеансе. Проверка численной сходимости и неопределённость физических параметров сохраняют прежние ограничения.

### Формат и совместимость

- Формат `format_version=1`, модель `conservative-1d-advection-dispersion-v1`. При изменении поддерживаемого формата или численной реализации необходимо явно изменить соответствующий идентификатор и правила совместимости. Повторный расчёт после обновления численной реализации не обещает побитово прежний результат.
- `conditions` содержит все параметры в единицах, указанных в именах: расходы — м³/с, концентрации — мг/л, скорость — м/с, дисперсия — м²/с, расстояния — м, времена — ч. Сохраняются длительность расчёта, режим нагрузки и длительность конечного периода; для постоянного режима период равен `null`.
- Реальное русло: устойчивый `reach_id`, версия подготовки `river-wgs84-v1`, SHA-256 основной линии и проверенного продолжения, положение источника в метрах от начала, название и сведения об источнике геометрии. Длина определяется руслом. Для синтетики сохраняется заданная длина, источник в начале, версия `synthetic-wgs84-meridian-v1`.
- Изменённая основная линия, продолжение, удалённый участок или неподдерживаемая версия не подменяются другим участком. Запись остаётся в библиотеке; открытие сообщает причину несовместимости, форма сохраняется. Геометрия сравнивается по нормализованному JSON, а не по переводу строк файла.
- Время создания хранится в PostgreSQL с часовым поясом; API возвращает дату ISO 8601, интерфейс показывает местное время браузера.

### API и ограничения хранения

`POST /api/v1/scenarios` создаёт запись, `GET /api/v1/scenarios?limit=20&offset=0` возвращает краткий список, `GET /api/v1/scenarios/{UUID}` — исходные условия и `compatibility: {compatible, reasons}`. Операций перезаписи и удаления нет. Создание требует `name`, `format_version`, `model_id`, `geometry_version`, `geometry_sha256` и `conditions` с контрактом существующего запроса расчёта; синтетический checksum — `null`.

Сервер проверяет конечность чисел, диапазоны, режим нагрузки, идентификатор/версию/контрольную сумму русла, остаток не менее 100 м и пригодность проверенного выходного буфера. Сохранение не запускает интегратор: ресурсные ограничения конкретного расчёта дополнительно проверяются при явном запуске. Запрос ограничен 8192 байтами до разбора JSON, объект условий в БД — 4096 байтами, сведения о геометрии — 2048 байтами. Создание принимает только `Content-Type: application/json` (параметр `charset` допустим); обычные формы и текстовые запросы отклоняются кодом 415 до чтения тела. Межсайтовый доступ CORS не включён. Список выдаёт не более 50 записей за запрос, `offset` — до 1 000 000; массивы результатов не принимаются. Общая библиотека растёт с числом сохранений и требует обычного резервного копирования базы.

Миграция `0003` добавляет только таблицу `saved_scenarios` и индекс даты; `0001` и `0002` не изменены. Штатный `docker compose up -d --build --wait` применяет её без удаления каталога, точек и Docker volume. При ошибке базы успешное сохранение не подтверждается. Если ожидание сохранения отменено или соединение оборвалось, обновите список перед повтором: сервер мог успеть записать условия.

Расчёт и привязка источника защищены от поздних ответов. Если во время расчёта начать редактировать источник, завершившийся расчёт сохраняется, а карта продолжает выполнять начатое редактирование. Привязка и операции библиотеки ограничены ожиданием 10 с. Ошибка привязки сохраняет прежнее положение; отменённый ответ не перемещает источник. Открытие условий, во время которого пользователь изменил форму, не заменяет эти изменения.

Для ручной проверки: выберите Воронеж у Жёлтых Песков, источник 40,125 м, расчёт 0,1 ч, конечный период 0,001 ч → сохраните условия → перезагрузите страницу → откройте запись → рассчитайте → закрепите А → создайте Б → уменьшите `ce` со 100 до 50 мг/л → сохраните под новым названием → явно рассчитайте Б. Сравните карту и графики на общем физическом времени. Эти параметры синтетические и не описывают фактический сброс.

Запись браузерных тестов выполняется только в отдельную временную БД. Для `frontend/tests/saved-scenarios-api.spec.ts` необходимы `SCENARIO_TEST_API` с адресом отдельного экземпляра backend и `SCENARIO_TEST_DB` вида `water_test_<32 hex>`. Без них восемь пишущих сквозных тестов пропускаются; обычные регрессии библиотеки используют подменённые ответы. Не направляйте проверочный экземпляр на рабочую базу. Временную базу создают, мигрируют и удаляют отдельно от рабочего Docker volume; базовый серверный набор по-прежнему запускается через `python run_tests.py`.

Проверка этапа (27.10.2026): **335 backend-тестов** в отдельной временной базе и **159 frontend-проверок** (152 браузерная Chromium, 4 математические и 3 конфигурационные), TypeScript/Vite и контейнерная сборка. Пишущие сквозные проверки включены и выполнены на отдельном API: Дон, Воронеж и синтетика, оба режима, дробные значения, крайний источник, сохранение изменённой формы при старом результате, перезагрузка и А/Б после явного расчёта. Реальный перезапуск проверочного backend сохранил все 20 записей без изменений; рабочие три объекта, четыре точки и исходный volume сохранены. Регрессии покрывают задержанные/отменённые ответы расчёта, привязки и открытия, тайм-аут привязки, ошибки БД и фиксации транзакции, неизвестный участок и изменение контрольных сумм/версий. Реальный телефон, Firefox/Safari, нагрузочное испытание библиотеки и публичный многопользовательский доступ не проверялись; авторизации нет, приложение предназначено для локального запуска.

В заключительном общем frontend-прогоне 158 проверок прошли, одна мобильная навигация остановилась до загрузки приложения с `net::ERR_NO_BUFFER_SPACE` в Chromium. Отдельный последовательный повтор всех пяти размеров профиля и двенадцати проверок библиотеки прошёл: **17/17**. Код приложения и системные сетевые настройки ради этого сбоя не изменялись; все 159 проверок подтверждены с учётом повтора.

## Перенос условий и выгрузка результатов

В параметрах раскройте «Сохранённые условия». **«Выгрузить текущие условия JSON»** использует название из поля и текущую валидную форму; прежний результат на карте в файл не попадает. Кнопка **«JSON ↓»** у записи библиотеки выгружает именно сохранённый набор, независимо от редактируемых полей. Массивов концентраций, состояния просмотра и пары А/Б в файле условий нет.

Выберите локальный файл через **«Импортировать условия JSON»**. После проверки появляется предварительный просмотр: название, участок, источник, параметры, нагрузка и совместимость. Только **«Применить к форме»** восстанавливает условия. Проверка и применение не запускают расчёт, не создают запись библиотеки и не заменяют А. Затем отдельно нажмите «Рассчитать»; сохранение в библиотеку также выполняется отдельно. Экспорт и просмотр файла сохраняют время и положение карты; применение физических параметров при прежней геометрии сохраняет показанный результат с предупреждением об изменении условий.

### JSON условий, версия 1

Кодировка UTF-8, размер **1–8192 байта**, проверяется до чтения и разбора на клиенте и до разбора на сервере. Серверная операция `POST /api/v1/scenario-files/validate` только проверяет файл, не обращается к БД и не запускает интегратор. Тело — исходный JSON, `Content-Type: application/json`; повторяющиеся ключи, повреждённые/неполные данные и неизвестные поля отклоняются. Неизвестная версия, модель, удалённый участок и изменённая основная линия или продолжение дают конкретную причину несовместимости, без подстановки другого русла. Текст файла показывается обычным текстом; адреса из него не открываются и не загружаются.

Файл содержит `name`, `format_version=1`, `model_id=conservative-1d-advection-dispersion-v1`, `geometry_mode`, `geometry_version`, `geometry_sha256`, `downstream_geometry_sha256`, `reach_id`, `reach_name`, `geometry_source` и `conditions`. Сведения об источнике геометрии — не свидетельство фактического сброса. Совместимость проверяется общими правилами библиотеки, включая остаток 100 м и пригодность проверенного продолжения.

Все поля `conditions` обязательны даже там, где API расчёта допускает значения по умолчанию: `river_flow_m3_s`, `effluent_flow_m3_s`, `background_mg_l`, `effluent_mg_l`, `velocity_m_s`, `dispersion_m2_s`, `length_m`, `duration_hours`, `load_mode`, `load_duration_hours`, `reach_id`, `source_distance_m`. Единицы — м³/с, мг/л, м/с, м²/с, метры и часы соответственно. Для реального русла `length_m=null`, длина определяется геометрией; для синтетики сохраняется заданная длина, `reach_id=null`, `source_distance_m=0`, обе контрольные суммы равны `null`. Для постоянной нагрузки `load_duration_hours=null`. Экспорт сохранённой записи не переносит её UUID или дату создания в другую библиотеку.

### CSV завершённого расчёта, версия 1

В панели профиля раскройте **«Экспорт численных результатов»**. **«Скачать C(x) CSV»** выгружает все центры сегментов в выбранный физический момент; **«Скачать C(t) CSV»** — всю сохранённую историю выбранного сегмента. До завершённого расчёта действия недоступны с объяснением. Изменённые поля формы не используются: выгружаются условия и версии именно завершённого результата.

CSV — UTF-8, разделитель **запятая**, десятичная точка, окончания строк CRLF, экранирование RFC 4180: поле с запятой, кавычкой или переводом строки заключается в кавычки, внутренние кавычки удваиваются. Числа записываются с точностью обратимого представления JavaScript Number, без округления подписей интерфейса. Близкие времена остаются отдельными строками.

После заголовка идёт строка `record_type=metadata`; её поле `metadata_json` содержит обычный JSON: `csv_format_version`, вид профиля, выбранное время или сегмент, единицы, смысл средних концентраций, происхождение сценария, а также условия, обозначение модели/формата, участок, положение источника, SHA обеих линий, атрибуцию/лицензию и сведения о временном разрешении каждого завершённого расчёта. Остальные строки имеют `record_type=data`. Метаданные следует сохранять вместе с численными строками.

Численные столбцы: `time_hours`, `distance_from_source_m`, `segment_index` (с 1) и `concentration_mg_l`. Расстояние отсчитывается от сценарного источника, концентрация — **расчётная средняя сегмента**, не наблюдение. В сравнении вместо одной концентрации записываются `concentration_A_mg_l`, `concentration_B_mg_l`, `delta_B_minus_A_mg_l`. Столбец `method` или `method_A`/`method_B` различает `saved_state` и `linear_interpolation`; интерполяция не выдаётся за дополнительный шаг интегратора.

История А/Б использует отсортированное объединение всех сохранённых времён обеих сеток, с независимой интерполяцией каждого сценария. Максимум при нынешних ограничениях — 4094 момента (по 2048 состояний с общими концами). Выгрузка не зависит от страницы таблицы и переключения активного А/Б; шкала, просмотр и сама карта не изменяются. Пространственный профиль ограничен имеющимися отображаемыми сегментами (не более 200), а не открытой частью таблицы.

Проверка этапа (29.10.2026): **408 backend-тестов** в одноразовой БД и **179 frontend-проверок** (172 браузерные, 4 математические, 3 конфигурационные), TypeScript/Vite и Docker build. Пишущие проверки библиотеки выполнялись только в отдельной временной базе. Проверены оба порядка поздних открытий, отдельные сообщения библиотеки, шесть реальных JSON roundtrip для Дона/Воронежа/синтетики и обоих режимов, дроби и крайний источник, отсутствие автоматических действий, повреждённые/большие/несовместимые файлы, отмена выбора, безопасность текста и клавиатура. CSV независимо разобран стандартным Python `csv` и `json`; проверены 4094 момента А/Б, экранирование и точные значения, неизменность выгрузки при переключении.

В пятисекундном сценарии `Qr=10`, `q=0,1`, `cb=10`, `ce=100`, `u=1`, `D=5`, `L=500`, горизонт 1 ч, нагрузка 5 с выгружены все **170** сохранённых состояний. Максимум первого сегмента **10,505969208918035 мг/л в 5 с** совпадает с результатом API; сохранение CSV не теряет пик. Независимая проверка C(x) допускает не более `5e-12` мг/л расхождения при временной интерполяции. Это проверка переноса уже рассчитанных чисел; точность самой схемы и физических исходных данных ею не подтверждается.

В браузере пройдены экспорт формы при старом результате, экспорт исходной записи, перезагрузка, предварительный просмотр, явное применение/расчёт и обе CSV-выгрузки на 1280×720 и 375×667, в том числе сохранение с клавиатуры. Физический телефон, Firefox/Safari и нагрузочное испытание не проверялись. PDF, Excel и импорт измерений не добавлены; физическая модель, география, зависимости и схема БД не изменены.

## Сохранение и восстановление

Исходники сохраняются локальными коммитами в рабочей ветке. Коммит не включает базу, `.env`, скачанные зависимости и результаты тестов. Для возврата к предыдущей версии кода предпочтительна отмена нужного коммита через `git revert` после проверки несохранённой работы и совместимости схемы.

Остановка и повторный запуск Compose сохраняют данные в томе `water-observation_water-data`. Резервную копию базы можно получить так (каталог исключён из Git):

```powershell
New-Item -ItemType Directory -Force backups | Out-Null
$backupName = 'water-' + (Get-Date -Format 'yyyyMMdd-HHmmss') + '.dump'
docker compose exec -T db pg_dump -U water -d water -Fc -f /tmp/water-backup.dump
if ($LASTEXITCODE -eq 0) { docker compose cp db:/tmp/water-backup.dump "backups/$backupName" }
```

Сохраняйте `.env` отдельно в защищённом месте. Перед восстановлением определите требуемые версию кода, ревизию миграций и копию базы. Сначала восстановите архив через `pg_restore` в отдельную пустую базу и проверьте результат; не перезаписывайте рабочую базу без отдельного решения. Откат `0003` удаляет библиотеку условий, откат `0002` — точки, сохраняя водные объекты; откат `0001` удаляет и таблицу объектов. Откат миграций не является повседневным способом восстановления.
