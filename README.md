# Наблюдения за водой

Локальная учебная основа веб-ГИС: каталог водных объектов с поиском и фильтрами, связанные точки наблюдения на карте и сценарный расчёт переноса растворённых хлоридов. Данные каталога поступают из PostgreSQL/PostGIS через FastAPI в React; расчёт выполняется отдельным модулем Python без обращения к базе.

Тема проекта: «Разработка геоинформационной системы моделирования распространения загрязняющих веществ в поверхностных водах Липецкой области».

Демонстрационный набор содержит **только синтетические записи**: учебную реку, озеро, водохранилище и четыре точки. Координаты вымышлены, положение точек на реальных водных объектах не подтверждено. Они не являются реальными станциями Липецкой области. Происхождение отмечено в базе (`is_synthetic`, `coordinate_source`), API и интерфейсе. Измерений, проб и импорта пока нет.

## Требования

- Docker Desktop с работающим движком Linux-контейнеров и Docker Compose.
- Git для истории исходников.
- Для дополнительных локальных проверок: Node.js 24 LTS с npm и Python 3.14. Для запуска через Compose отдельная установка PostgreSQL и Python-пакетов не требуется.

Начальная проверенная среда: Git 2.53.0, Node.js 24.21.0, npm 11.19.0, Python 3.14.1, Docker 29.8.2, Compose 5.6.0. Точные зависимости находятся в `frontend/package-lock.json` и `backend/requirements.txt`; прямые Python-зависимости — в `backend/requirements.in`.

## Первый запуск в Windows

Откройте PowerShell в папке проекта. Создайте локальный файл настроек, только если его ещё нет:

```powershell
if (-not (Test-Path .env)) { Copy-Item .env.example .env }
```

Перед первым запуском задайте собственный пароль в поле `POSTGRES_PASSWORD` файла `.env`. Этот файл исключён из Git. При уже созданном томе базы изменение только `.env` не меняет пароль пользователя PostgreSQL.

```powershell
docker compose up -d --build --wait
docker compose exec backend python -m app.seed
```

Первый запуск скачивает образы и зависимости. Миграции применяются при старте backend. Заполнение учебными объектами и точками выполняется отдельно и повторно не создаёт дубликаты; существующие записи и координаты не перезаписываются. К изменённым родительским демонстрационным объектам точки автоматически не присоединяются. Без заполнения показывается корректный пустой список.

- Интерфейс: <http://localhost:5173>
- API: <http://localhost:8000/api/v1/water-bodies>
- Описание API: <http://localhost:8000/docs>

Проверьте, что на экране три учебных объекта, их типы и маркировка «Синтетические данные». Нажмите «Обновить список». Данные приходят из базы, а не из встроенного массива интерфейса.

Введите часть названия, например `УЧЕБ`, выберите «Озёра» и нажмите «Применить» или Enter в поле поиска. Останется учебное озеро. Поиск не учитывает регистр, включая кириллицу и `ё`; пробелы по краям убираются. Пустой запрос не ограничивает название, «Все типы» не ограничивает тип. `%` и `_` ищутся как обычные символы. Поиск выполняется по подстроке, без морфологии и замены `ё` на `е`.

Изменение полей само по себе не отправляет запрос: действующие условия подписаны под формой. «Обновить список», повтор после ошибки и переходы между страницами сохраняют применённые условия. Применение или сброс возвращает на первую страницу. «Сбросить условия» очищает оба поля и сразу загружает полный список. Для проверки отсутствия совпадений совместите `РЕКА` с типом «Озёра»: интерфейс предложит изменить или сбросить условия. Пустая база имеет отдельное сообщение.

Повторный запуск: `docker compose up -d --wait`. После изменения исходников используйте `docker compose up -d --build --wait`. **Перед обновлением существующей базы с ревизии `0001` сделайте резервную копию по инструкции ниже:** запуск нового backend применяет миграцию `0002`, добавляющую точки. Затем отдельно выполните `docker compose exec backend python -m app.seed`, чтобы добавить демонстрационные точки. Применённая миграция `0001` не изменена.

У frontend есть HTTP healthcheck: ожидание готовности проверяет успешный ответ страницы и наличие входного модуля интерфейса. Остановка: `docker compose down`. Именованный том с данными сохраняется. **Не добавляйте `-v` к команде остановки: этот параметр удаляет том базы.**

## Точки наблюдения и карта

Нажмите название водного объекта в каталоге. У учебной реки три точки: две с координатами и одна без них. У озера одна точка, у водохранилища — пустой список. Нажмите точку в списке или её пронумерованный маркер: выбор синхронизируется, а карточка загружается отдельным запросом API. В ней показаны название, водный объект, долгота, широта и источник координат. Список и маркеры доступны с клавиатуры; маркер выбирается Enter или пробелом.

Точки без координат доступны в списке и карточке, но не имеют маркера; их количество указано отдельно. Если координат нет у всех точек, карта заменяется пояснением. При сбое подложки появляются сообщение и кнопка повтора, список и карточка продолжают работать. Цвет и обводка маркера обозначают только выбор, а не качество воды. Контуры водных объектов не строятся.

«Вернуться к каталогу» и кнопка «Назад» браузера сохраняют применённые поиск, тип и страницу в текущей вкладке. Состояние каталога хранится в памяти; перезагрузка страницы его сбрасывает. Экран объекта можно открыть ссылкой вида `http://localhost:5173/#water-body/<UUID>`.

Подложка — стандартные растровые тайлы [OpenStreetMap](https://www.openstreetmap.org/copyright) с видимой атрибуцией. Для локального интерактивного просмотра ключ и платный аккаунт не нужны. Используется HTTPS, стандартные Referer и кеш браузера; массового скачивания, предварительной загрузки и офлайн-карт нет. Доступность внешнего сервиса не гарантирована. Перед публичным развёртыванием или ростом нагрузки нужно заново проверить [политику тайлов OSM](https://operations.osmfoundation.org/policies/tiles/) и выбрать подходящий сервис. Запросы подложки передают серверу OSM обычные сетевые сведения браузера и область просмотра; имена точек не передаются.

Leaflet 1.9.4 поставляется с лицензией BSD-2-Clause; текст сохранён в `frontend/public/leaflet-license.txt` и доступен как `/leaflet-license.txt`. GeoAlchemy2 0.20.0 добавлен для связи SQLAlchemy с PostGIS; лицензия MIT сохраняется в установленном пакете. Версии зафиксированы в файлах зависимостей.

## Состав проекта

- `frontend/src/` — экран, состояния запросов и оформление; Vite передаёт `/api` в backend.
- `backend/app/` — подключение к базе, модель, API и отдельное заполнение учебными данными.
- `backend/migrations/` — начальная схема Alembic и включение PostGIS.
- `backend/tests/` и `backend/run_tests.py` — проверки на настоящем PostgreSQL в отдельной временной базе.
- `frontend/tests/` — браузерные сценарии Playwright.
- `compose.yaml` — база PostgreSQL 18/PostGIS 3.6, backend и интерфейс.

Сервисы доступны только через `127.0.0.1`: интерфейс — порт 5173, backend — 8000, база — 55432. Это локальное окружение разработки, без авторизации и публичного развёртывания. Для интерфейса используется сервер Vite; production-сборка также проверяется при создании образа.

SQLAlchemy отвечает за запросы и ограничения модели, Alembic — за версионирование схемы, Psycopg — за соединение с PostgreSQL. Положение хранится только в одном nullable-поле PostGIS `geometry(Point,4326)`: отдельных изменяемых столбцов широты и долготы нет. База проверяет тип, SRID, двумерность, непустую геометрию, долготу −180…180 и широту −90…90; NaN и бесконечности запрещены. Координаты не переставляются и не исправляются автоматически. Точка связана внешним ключом с водным объектом; источник координат обязателен даже для синтетической записи, а для точки без положения указывается причина его отсутствия. Служебные таблицы расширения исключены из сравнения Alembic.

## API

`GET /api/v1/water-bodies?limit=50&offset=0&q=учеб&kind=lake`

Ответ содержит `items`, `total` (число совпадений во всей базе), `catalog_total` (число объектов без фильтра), `limit`, `offset`. У каждого объекта есть UUID `id`, `name`, `kind` (`river`, `lake`, `reservoir`) и обязательный `is_synthetic`. Записи упорядочены по названию и ID. Допустимый `limit`: 1–100; `offset` — неотрицательное целое число.

Необязательный `q` — подстрока названия, максимум 120 символов исходного параметра до удаления пробелов; нулевой символ запрещён. Необязательный `kind` допускает только `river`, `lake`, `reservoir`. Для всех типов параметр `kind` нужно опустить; пустое значение недопустимо. Условия соединяются через AND и применяются до пагинации. Лимиты проверяются на backend; SQL-шаблоны из пользовательского ввода не исполняются.

Пустая база и отсутствие совпадений возвращают `200` и `items: []`; их различает `catalog_total`. Неверные параметры поиска, типа или пагинации — `422`. Недоступность базы — `503` с нейтральным сообщением без строки подключения. Имён, координат и характеристик реальных объектов в демонстрационном наборе нет.

`GET /api/v1/water-bodies/{water_body_id}/observation-points` возвращает `water_body`, полный массив `items` и `total`. В этом этапе коллекция точек не ограничена и не разбита на страницы: карта и список показывают весь набор выбранного объекта. Большие наборы потребуют отдельного решения по загрузке и отображению; интерфейс отвергает ответ, если `total` не совпадает с длиной массива.

`GET /api/v1/observation-points/{point_id}` возвращает отдельную точку и её `water_body`. Поля точки: `id`, `name`, `water_body_id`, `is_synthetic`, `coordinate_source`, `geometry`. Геометрия — GeoJSON `{"type":"Point","coordinates":[39.25,52.75]}`: **долгота, широта**, WGS 84 / EPSG:4326; отсутствие положения — `null`. Leaflet получает преобразованный порядок широта/долгота только при отображении.

Неизвестный UUID объекта или точки — `404`, некорректный UUID — `422`, отсутствие точек у известного объекта — `200` с пустым `items` и `total: 0`, недоступность базы — `503`. API создания и изменения точек в этот этап не входит.

## Сценарное моделирование

После запуска Compose откройте `http://localhost:5173/#model` или раздел «Моделирование». Нажмите «Рассчитать» с демонстрационными параметрами. Перемещайте время от 0 до 24 часов, выбирайте сегмент на карте или в списке: карта, профиль и таблица показывают одни и те же значения API. Шкала концентраций фиксирована на весь расчёт. Все концентрации — средние по отображаемым сегментам, расстояния подписаны для их центров.

Изменение формы не пересчитывает результат автоматически. До нового запуска прежний результат маркируется как относящийся к предыдущим условиям; его входные параметры доступны под профилем. При ошибке можно повторить запрос. Новый запрос отменяет ожидание старого, запоздалый ответ не заменяет актуальный. «Отменить ожидание» отменяет ожидание в браузере; сервер может завершать уже начатый ограниченный расчёт. Запуски не сохраняются в БД и после ухода из раздела теряются.

Геометрия, выпуск и гидрологические параметры полностью **синтетические** и не относятся к предприятию. Демонстрационная линия идёт на север по меридиану WGS84 от произвольно выбранной точки 40° в.д., 52,3° с.ш. Это условная линия, не подтверждённое русло. Её координаты вычисляются backend через интеграл меридионального радиуса эллипсоида и обратное решение длины дуги; градусы и пиксели не используются как метры. Независимый контроль `PostGIS ST_Length(geography)` проверяет общую длину и сегменты с допуском 1 см. Отображаемые 100 сегментов покрывают ровно заданную длину; выходной буфер в карту не включён. Источник сброса и расчётный участок не создают записей точек наблюдения.

### Постановка и численный метод

Модель описывает полностью перемешанное сечение после зоны смешения, один консервативный растворённый компонент и постоянную гидравлику. Учитываются течение и продольная дисперсия. Нет притоков, водозаборов, распада, сорбции, донного обмена и подпора. Волна изменения расхода при открытии выпуска не рассчитывается. Модель не предназначена для озёр, водохранилищ, струи возле трубы или нормативной оценки.

Внутри ядра используются м, с, кг/м³; `1 мг/л = 0,001 кг/м³`. При `Q = Qr + q` и `A = Q/u` решается:

```text
∂(A c)/∂t + ∂J/∂x = 0
J = Q c − A D ∂c/∂x
c(x,0) = cb
J(0,t) = Qr cb + q ce
∂c/∂x(Lcalc,t) = 0
```

Вход — полный массовый поток, не фиксированная концентрация. Расчётный буфер равен как минимум `max(0,1 L, 20 D/u)` с округлением вверх до целой ячейки. Для устойчивого учёта малого превышения решатель переносит `c−cb`, а затем добавляет постоянный фон: вход избыточной массы равен `q(ce−cb)`. Отрицательное превышение при чистых стоках допустимо, отрицательная полная концентрация не обнуляется искусственно.

Применены конечные объёмы с экспоненциально согласованным потоком между ячейками (Scharfetter–Gummel) и схема Crank–Nicolson по времени. Для шага `dx`, `Pe=u dx/D` поток на единицу площади между соседями имеет вид:

```text
j = u/(1−exp(−Pe)) · c_left − u/(exp(Pe)−1) · c_right
```

Один и тот же поток входит в соседние ячейки с противоположным знаком, обеспечивая баланс массы. `Pe ≤ 0,5`; шаг времени ограничен так, чтобы правая часть Crank–Nicolson оставалась неотрицательной, а матрица неявного шага была M-матрицей. Трёхдиагональная система решается методом прогонки. Обнуления отрицательных значений и искусственного затухания нет. Зависимости для вычислений не добавлены: ядро использует стандартную библиотеку Python.

Сначала по участку проходит и размывается фронт. При установившемся режиме концентрация `c∞=(Qr cb+q ce)/(Qr+q)` постоянна вдоль участка. `L/u` — характерное время переноса, не точный момент первого появления. Результат API содержит 49 временных срезов, включая начальный и конечный, и 100 средних по отображаемым сегментам. Внутренняя сетка мельче; усреднение сохраняет массу.

Для демонстрации: `Qr=10`, `q=0,1` м³/с; `cb=10`, `ce=100` мг/л; `u=0,25` м/с; `D=5` м²/с; `L=10000` м; длительность 24 ч. Контрольные величины: `A=40,4 м²`, нагрузка выпуска `0,010 кг/с`, сверх фона `0,009 кг/с`, `c∞=10,891089… мг/л`, `L/u=11,111… ч`. Сетка этого примера: 1100 ячеек по 10 м, буфер 1000 м, 5520 временных шагов примерно по 15,652 с.

### API и ограничения размера

`POST /api/v1/simulations`, JSON:

```json
{
  "river_flow_m3_s": 10,
  "effluent_flow_m3_s": 0.1,
  "background_mg_l": 10,
  "effluent_mg_l": 100,
  "velocity_m_s": 0.25,
  "dispersion_m2_s": 5,
  "length_m": 10000,
  "duration_hours": 24
}
```

Допустимы только конечные JSON-числа; строки, логические значения, лишние и пропущенные поля отклоняются. Диапазоны: `Qr 0,1–1000`, `q 0–100 м³/с`; `cb/ce 0–10000 мг/л`; `u 0,02–2 м/с`; `D 0,1–100 м²/с`; длина `100–20000 м`; длительность `0,1–48 ч`. Дополнительно до расчёта проверяются пределы: 6000 ячеек, 15000 шагов и 20 млн операций «ячейка × шаг». Поэтому некоторые сочетания допустимых отдельных значений отвергаются: нужно сократить участок/время или изменить физические параметры сценария. Размер входного тела ограничен 4096 байт, включая потоковые запросы. В одном процессе backend выполняется не более одного расчёта; очереди задач нет.

Ответ: `inputs`, `derived`, `distances_m`, `times_hours`, `concentrations_mg_l[time][segment]`, `geometry` (GeoJSON, долгота/широта), `scale_mg_l`, `diagnostics`, `provenance=synthetic`. Размеры массивов фиксированы, ответ демонстрации меньше 250 КБ. Ошибки: `422` — параметры/стоимость задачи, `413` — размер тела, `503` с `Retry-After` — занятый вычислитель. API не зависит от записей в БД, но запуск Compose сохраняет прежнюю проверку доступности каталога.

### Численная проверка

Ядро проверяется отдельно от API, карты и PostgreSQL:

```powershell
docker compose exec backend python -m pytest solver_tests -q -s
```

Для запуска без Docker из `backend` при установленных зависимостях проекта: `python -m pytest solver_tests -q -s`. Полный backend-набор, включая ядро и интеграционные проверки, запускается через `docker compose exec backend python run_tests.py -q`; он использует отдельную временную базу, а не рабочие записи. Браузерные проверки: `npm.cmd test` из `frontend` при работающем Compose.

Независимый точный контроль выведен в `solver_tests/test_numerical_accuracy.py`: собственная мода уравнения с теми же потоковой входной и нулевой градиентной выходной границами, но с неравномерным начальным профилем. При `a=u/(2D)`:

```text
c = B + exp(a x) [cos(k x) + (a/k) sin(k x)] exp(−λt)
λ = D k² + u²/(4D)
2 a k cos(k L) + (a²−k²) sin(k L) = 0
```

Подстановка даёт вход `u B` на единицу площади и нулевую производную на выходе. Сравниваются точные средние по ячейкам, полученные аналитическим интегрированием, а не значения в центрах. Непроверенная формула из внешнего документа не используется как эталон.

Проверки включают единицы, отсутствие источника (`q=0`, `ce=cb`), чистые стоки, балансы полной и избыточной массы, установившийся предел, влияние параметров, сеточную сходимость и удвоение буфера. Допуски:

| Проверка | Допуск и смысл |
|---|---|
| Балансы массы | Относительная невязка менее `10⁻⁹`; это контроль дискретного сохранения, не точности полевых данных |
| Точная собственная мода | RMS менее `2·10⁻⁵ кг/м³` на 80 ячейках; при удвоении сетки ошибка должна уменьшаться более чем в 3,7 раза — проверка второго порядка |
| Уточнение времени | На фиксированной сетке ошибка должна уменьшаться более чем в 3,8 раза; сравнение с малым временным шагом отделяет временную ошибку от пространственной |
| Демонстрация, первые 6 ч | Максимальная разница всех срезов при `dx/2` менее `0,003 мг/л`, при `dt/2` менее `0,0002 мг/л`; примерно 0,34% и 0,023% от превышения над фоном |
| Удвоение буфера | Разница на отображаемом участке менее `10⁻⁷ мг/л`, в том числе после прохождения фронтом конца участка |
| Установившийся предел | Максимальное отличие демонстрации на 24 ч менее `10⁻⁶ мг/л` |

Итоговая проверка этапа: **115 backend-тестов** (включая 24 независимых теста ядра) и **44 браузерных сценария Chromium**, сборка TypeScript/Vite, `pip check`, `alembic check` и готовность трёх контейнеров. Сохранность прежних записей подтверждена совпадением контрольных сумм. В браузере проверены настоящий API, соответствие карты/профиля/таблицы, отмена ожидания, ошибки, устаревшие ответы и размеры экрана 375–1440 px.

Для демонстрации максимальная разница первых 6 ч при `dx/2` составила `0,00172422 мг/л`, при `dt/2` — `0,000132187 мг/л`; удвоение буфера в проверенных срезах 6 и 15 ч не изменило результат в машинном представлении. RMS точной собственной моды на 20/40/80 ячейках: `2,48864·10⁻⁴ / 6,24086·10⁻⁵ / 1,56142·10⁻⁵ кг/м³`. На 24 ч относительные невязки полной и избыточной массы составили около `1,30·10⁻¹⁴` и `1,62·10⁻¹³`.

Эти допуски проверяют выбранные контрольные случаи; они не являются гарантией одинаковой ошибки для каждого допустимого набора параметров. Программа не откалибрована по реальным наблюдениям. Для такой проверки нужны согласованные по времени расход и концентрация стоков, фон выше выпуска, гидрология и несколько створов ниже. Настройку параметров и независимую проверку следует проводить на разных данных. Firefox, Safari, нагрузка и публичное развёртывание на этом этапе не проверялись.

## Сценарий по реальному руслу

В разделе «Моделирование» выберите «Реальное речное русло». Подготовлен **Дон ниже Ольховца**, Лебедянский район Липецкой области: **3126,043 м**, от `53.0802087 N, 39.1723162 E` до `53.0584623 N, 39.1799942 E`. Геометрия — OpenStreetMap way **30428409 v32**, WGS84; сохранён исходный порядок вниз по течению. Положение сверено с независимой Esri World Imagery. Мост выше начала исключён; участок и проверенное продолжение заканчиваются до следующего отображённого притока. Полные идентификаторы, источники, условия ODbL, ограничения картографической проверки и подготовка описаны в [паспорте участка](docs/river-data.md).

Задайте «Положение сценарного источника, м» числом или ползунком. Маркер показывает условную границу **после полного смешения**, а не предприятие, фактический выпуск или струю возле трубы. Отсчёт идёт от верхней границы подготовленного участка. Расчётная длина определяется оставшейся геометрией ниже источника и недоступна для произвольного изменения. Нужно оставить не менее 100 м русла.

Нажмите «Рассчитать». Для просмотра фронта с исходными параметрами выберите примерно 1–3 ч. Кнопки воспроизведения/паузы, скорость 0,5×–4× и перемотка управляют одним временем карты, профиля и таблицы. При 1× вся длительность воспроизводится примерно за 24 секунды активного просмотра. Между 49 вычисленными моментами применяется **линейная интерполяция рассчитанных концентраций**; она подписана в интерфейсе и не означает дополнительное решение уравнения. Воспроизведение начинается только по кнопке, останавливается при перемотке и в конце. Шкала неизменна на протяжении одного расчёта; движение цвета не заменяет численные значения.

Расстояния и границы сегментов вычисляет GeographicLib 2.1 на эллипсоиде WGS84. Внутри каждого из 100 отображаемых сегментов сохраняются исходные вершины русла; сегмент не заменяется хордой между его границами. Расстояния профиля отсчитываются от сценарного источника. Предварительный маркер до запуска интерполируется между ближайшими вершинами для отображения; точное положение границы результата рассчитывает backend геодезическим методом.

Пользовательские расходы, концентрации, скорость и дисперсия остаются сценарными. Средний модельный расход из геоданных не подставляется. Расчётная гидравлика постоянна; реальная геометрия не подтверждает это допущение. Проверка концентраций по наблюдениям не выполнена. Не учитываются ветвления, другие сбросы, озёра, водохранилища, химические реакции и локальная зона смешения.

Ниже отображаемого конца проверено ещё **1370,250 м** русла для вычислительного буфера. Если требуемый ядром буфер выходит за это продолжение или задача превышает вычислительные ограничения, API возвращает понятную ошибку и **не изменяет параметры автоматически**. Например, остаток 100 м при `D=5 м²/с`, `u=0,25 м/с` и длительности 2 ч превышает лимит шагов; отдельно проверен допустимый сценарий 0,1 ч с теми же остальными параметрами.

`GET /api/v1/river-reaches` возвращает подготовленную линию, накопленные расстояния вершин, метаданные и SHA-256 геометрии. В реальном запросе `POST /api/v1/simulations` передавайте семь физических параметров без `length_m`, а также `reach_id="don-olkhovets"` и `source_distance_m`. Произвольный `length_m` с реальным руслом отклоняется. Ответ содержит вычисленную длину в `inputs`, идентификатор и положение источника, его координаты, `reach_metadata`, общую линию и `segment_geometries` с сохранёнными изгибами. Синтетический запрос из восьми параметров продолжает работать.

Подготовка повторяется без сети и без изменения базы:

```powershell
backend/.venv/Scripts/python.exe backend/scripts/prepare_river.py
```

Тесты проверяют воспроизводимость снимка, разбиение и сохранение вершин, независимые длины PostGIS с допуском 1 мм относительно той же полилинии, источник в начале/середине/у конца, отказ короткого остатка и неподходящего буфера, неизменность баланса массы и синтетического режима. Этот допуск относится к вычислению расстояний, а не к точности картирования русла. Исходный XML сохраняется побайтово; GeoJSON создаётся с одинаковыми переводами строк на Windows и Linux. Новые таблицы и миграции не добавлены.

Итоговая проверка руслового этапа: **138 backend-тестов** и **50 браузерных тестов Chromium** прошли, TypeScript и production-сборка Vite успешны. Проверены воспроизведение, пауза, скорость, перемотка, совпадение карты/профиля/таблицы, адаптивный интерфейс и прежние сценарии каталога, поиска и точек наблюдения. Браузерные автотесты отключают внешние тайлы; доступность настоящей подложки отдельно проверена вручную. Контрольные суммы трёх сохранённых водных объектов и четырёх точек не изменились. Firefox, Safari, нагрузка и публичное развёртывание не проверялись.

## Сохранение и восстановление

Исходники сохраняются локальными коммитами в рабочей ветке. Коммит не включает базу, `.env`, скачанные зависимости и результаты тестов. Для возврата к предыдущей версии кода предпочтительна отмена нужного коммита через `git revert` после проверки несохранённой работы и совместимости схемы.

Остановка и повторный запуск Compose сохраняют данные в томе `water-observation_water-data`. Резервную копию базы можно получить так (каталог исключён из Git):

```powershell
New-Item -ItemType Directory -Force backups | Out-Null
$backupName = 'water-' + (Get-Date -Format 'yyyyMMdd-HHmmss') + '.dump'
docker compose exec -T db pg_dump -U water -d water -Fc -f /tmp/water-backup.dump
if ($LASTEXITCODE -eq 0) { docker compose cp db:/tmp/water-backup.dump "backups/$backupName" }
```

Сохраняйте `.env` отдельно в защищённом месте. Перед восстановлением определите требуемые версию кода, ревизию миграций и копию базы. Сначала восстановите архив через `pg_restore` в отдельную пустую базу и проверьте результат; не перезаписывайте рабочую базу без отдельного решения. Откат `0002` удаляет точки, сохраняя водные объекты; откат `0001` удаляет и таблицу объектов. Откат миграций не является повседневным способом восстановления.
